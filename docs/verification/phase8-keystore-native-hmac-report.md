# Phase 8 — Keystore-native HMAC provider (ACCEPTED WITH DOCUMENTED LIMITATIONS)

Continuation of `keystore-key-isolation-report.md`. That report moved the HMAC key
out of a file; this one removes the key from the Node process entirely, has the
Android Keystore compute every MAC, rotates the existing v1 manifests under the
new authority after verifying them, and states exactly where signing authority
still leaks.

Repository `HEAD` before and after: `b945d72756199f004624a980127fdec5c56be6ce`.
Nothing was committed, staged, pushed, reset, cleaned or checked out.
Device: Samsung Galaxy A07, serial `R8YY90VT4EM`, preview package
`com.openmausbot.companion.preview`, official package untouched and running.

## 2. Trust boundaries and threat model

| Component | Runs as | Can reach | Cannot reach |
| --- | --- | --- | --- |
| Android host service (`HarnessHost`, app process) | app UID `u0_a279` | Android Keystore, the child's stdin/stdout pipes, app-private files | other apps' data |
| Android Keystore (`keystore2`) | system | holds a non-exportable `HmacSHA256` key | never returns the key bytes |
| Embedded Node host (child of the app) | same app UID | its own stdio, app-private data, the phone's loopback | the Keystore key bytes (no API path for them) |
| `memory-store.ts` | the Node host | canonical records and manifests | key material |
| Agent file tools (`android_computer`, device-files capability) | the Node host / app | the bot workspace only; `isProtectedMemoryPath` refuses `memory/records*.json` and `memory-integrity/*` | canonical records, the marker, the bridge |
| Agent shell / terminal tools | app UID, same device | **everything the app can reach, including `/proc/<host>/fd/0` and `/fd/1`** | — (this is the documented hole) |
| Loopback HTTP | any local process with the app's authorization model | normal API routes | no MAC route exists |

The supported attacker for this phase is the one that writes files or runs
the packaged bundle **without** app-UID code execution. That attacker gets no
key, no MAC and no valid v1/v2 manifest.

The attacker that *does* execute as the app UID is out of scope by
construction: it can call the Keystore alias directly through the Java API, so
the bridge is not the weakest link and cannot be made one.

## 3. Native provider architecture

- [MemoryIntegrityKeyStore.kt](../../android/app/src/main/kotlin/com/openmausbot/companion/host/MemoryIntegrityKeyStore.kt)
  - `HMAC_ALIAS = "omb_memory_integrity_hmac_v2"` — `HmacSHA256` key generated by
    `KeyGenerator` with `AndroidKeyStore`, `PURPOSE_SIGN|VERIFY`, `setKeySize(256)`.
    Non-exportable; `KeyInfo` is consulted for the level, never assumed.
  - `mac(purpose, payload)` (line 105) computes `HMAC-SHA256("omb-memory-<purpose>-v1\n" + payload)`
    inside the Keystore and returns hex. Purpose must be `record` or `manifest`.
  - `prepare(dataDir)` (line 75) binds the data directory at spawn. If the alias
    is absent **and** `native-provider.json` exists, it throws `Unavailable`
    instead of minting a new key — the device-restore case fails closed.
  - `retireLegacyKey(dataDir)` deletes `key.keystore` and the old wrapping alias
    only after the host reports every store migrated.
- [HarnessHost.kt](../../android/app/src/main/kotlin/com/openmausbot/companion/host/HarnessHost.kt)
  - spawn env: `OMB_MEMORY_INTEGRITY_NATIVE=1` always; `OMB_MEMORY_INTEGRITY_LEGACY`
    is `1` only while the marker is absent and the retired blob still exists
    (line 252–253). No key is ever put in argv, env, or a file.
  - frame bridge (line 76): records travel as `\u001eOMBINT {json}` lines over the
    child's stdout; responses go back over the child's stdin. `validIntegrityPayload`
    (line 365) requires the full canonical record/manifest field set, caps the
    batch at 512, and rejects any unknown purpose. The bridge is not an HTTP
    route and is not registered in any capability.
  - on the `migrated` frame, `retireLegacyKey` deletes the blob; on later boots
    with the marker present the blob is retired before spawn.
- [memory-integrity.ts](../../server/memory-integrity.ts)
  - providers: `native` (Android), `stdin` (migration boots only), `file` (desktop).
  - `memoryIntegrityKey()` throws in native mode; no key is read, created or
    cached. `bridgeRequest` (line 240) writes a frame and blocks until the
    matching id comes back; EOF or a malformed reply raises
    `MemoryIntegrityError` → `500 ERR_MEMORY_INTEGRITY`.
  - v2 manifests carry `version: 2, provider: "keystore"`; v1 manifests are
    verified with the retired key and then re-sealed, never re-signed blindly.
- [memory-store.ts](../../server/memory-store.ts) `migrateMemoryIntegrityToNative`
  (line 871) runs the rotation pass and classifies outcomes; every authorization,
  redaction, lifecycle and reconciliation step stays where it was, before the
  canonical payload is formed.

### Why no `Promise` conversion

The provider is a **synchronous** round trip: Keystore `Mac` plus a blocking
pipe read, on a path whose callers (`putMemoryRecord`, `loadMemoryRecords`,
`queryPartitionedMemory`, `assembleMemoryForContext`, journal and route code)
are all synchronous today. The task allowed async only where the provider
required it. Converting would add no capability and would put a real risk in
place: an `await` between "records written" and "manifest sealed" is exactly the
window where a crash leaves a store that looks committed but is not
authenticated. The synchronous contract is preserved end to end; the atomic
write plus manifest write remain ordered, and any provider failure throws before
the caller can observe success.

A wedged harness therefore **blocks** the operation rather than returning
unverified data (no timeout is imposed inside `readSync`; the app's health
watchdog restarts a host that stops answering, and the pipe closes on harness
death, which fails closed). This is a latency property, not a trust property.

## 5. Signing-authority restrictions and residual risk

Enforced:

- No HTTP route, capability, or agent tool exposes a MAC. The only producers are
  `nativeMacBatch` calls inside `memory-integrity.ts`, reached from the canonical
  store after authorization, scope, confidence, redaction and lifecycle checks.
- The harness rejects unknown purposes and any payload that is not shaped like a
  canonical record or manifest, and caps a batch at 512.
- The purpose string is bound into the MAC input, so a record MAC cannot be
  replayed as a manifest MAC.
- Every read re-verifies record MACs, the digest and the manifest MAC before a
  snippet can reach context; a failure returns `500 ERR_MEMORY_INTEGRITY` and
  records an incident without record text.

Not enforced, measured:

```
$ adb shell "run-as com.openmausbot.companion.preview sh -c \
    'exec 9</proc/<host>/fd/0 && echo stdin-open-ok; exec 8>/proc/<host>/fd/1 && echo stdout-open-ok'"
stdin-open-ok
stdout-open-ok
```

`/proc/sys/kernel/yama/ptrace_scope` does not exist on this kernel, and the
pipes are owned by the app UID. Any code running as the app UID — including the
agent's own shell/terminal tools, which execute in the app process — can open
both ends of the bridge, inject a frame the harness will answer, and read the
resulting MAC. It can equally call the Keystore alias through the Java API,
which is why the bridge cannot be the boundary.

Consequences, stated plainly:

- The provider is a **signing oracle for canonical-shaped payloads to same-UID
  code**. It cannot be asked to sign arbitrary bytes, but it will MAC any
  payload that has the right keys.
- The agent's *file* tools cannot use this: the device-file surface refuses
  `memory/records(.integrity).json` and `memory-integrity/*` (covered by
  `refuses canonical records and integrity files through the device file surface`).
- The agent's *shell* tools can. This was true before this phase only in a
  weaker form (the key was in the Node process rather than a Keystore alias);
  the boundary that matters — same-UID code is trusted — is unchanged.
- Same-UID code can also read host memory, replace the bundle, or clear app
  data. Compromised-runtime and paired-rollback attacks remain out of scope.

## 6. Migration and rollback behaviour

Versioned rotation, because Android Keystore cannot import an existing HMAC key
(`KeyStore.setEntry` is not supported for `AndroidKeyStore` secrets):

1. The one boot that still sees `key.keystore` gets the retired key over the
   child's stdin (marker absent, blob present).
2. `migrateMemoryIntegrityToNative` walks the bot roster plus `shared`; each
   store is **loaded**, which verifies its v1 manifest with the retired key.
3. A verified store is re-sealed as v2 (`provider: "keystore"`, `seq` bumped):
   the manifest is rewritten, the records file is not touched.
4. A store the retired key **cannot** authenticate is recorded as `refused` in
   `native-provider.json`, its bytes are left exactly as they were, and it stays
   fail-closed. It does not block retirement: the retired key could never make
   it verify.
5. An **operational** failure (unreadable file, invalid JSON) is `blocked`, and
   no marker is written, so the retired key stays in service for the next boot.
6. A boot without the retired key (hand-started copy, marker already written)
   raises `MemoryIntegrityKeyUnavailableError` and is likewise `blocked`.
7. Once the pass completes, the marker is written and the harness deletes the
   blob and the wrapping alias — immediately on the `migrated` frame, and again
   on every later boot if either still exists.

The marker is the durable evidence. The current preview marker:

```json
{"v":2,"at":1792669376301,"migrated":[],
 "refused":[{"botId":"eb51a69f-…","reason":"ERR_MEMORY_INTEGRITY: record \"4fabc77d-…\" failed integrity verification"}]}
```

`migrated: []` because the two healthy stores were already re-sealed during the
first (failed) pass on this device; `refused` is the store left forged by the
Phase 7 tamper test. Its bytes are preserved in
`.omb-scratch/native-mig/eb51a69f-…/` (records + manifest) as evidence.

Crash safety: the marker is written only after the loop, with an atomic file
write; re-running is idempotent (already-v2 stores are skipped, `seq` is not
advanced again). A crash before the marker leaves the blob in place and the
next boot repeats verification against it.

Key loss / device restore: the marker survives, the alias does not. `prepare()`
refuses to mint a replacement when the marker exists, so the host starts with
no MACs and memory fails closed with `ERR_MEMORY_INTEGRITY` rather than
re-blessing old bytes under a new key.

Retirement assumption: the old key was delivered into Node memory on the
migration boot (and on every boot under the previous design), so this change
cannot prove it was never copied before today.

Rollback: a v1 manifest without the retired key fails (`this store is still
signed with the retired key: it did not verify during the Keystore migration…`).
A paired rollback of records + manifest to an earlier *v2* pair is still
undetectable — the marker records only completion, not a sequence anchor.

## 14. Remaining limitations and blocked tests

- **Same-UID signing authority** (measured, §5): anything running as the app UID
  can use the Keystore alias or the pipes. This includes the agent's shell
  tools. The bridge is not an authorization boundary against that attacker.
- **Software-backed Keystore** (`securityLevel=1`); no TEE/StrongBox claim.
- **Compromised runtime / bundle replacement** is outside the boundary.
- **Device restore** loses the key; `prepare()` refuses to mint a replacement,
  so memory fails closed until the install is recovered. The restore path itself
  was **NOT RUN** on the device (deleting the Keystore alias would have destroyed
  the only authority this install still has); it is covered by the code path and
  the marker check only.
- **Paired rollback** of records + manifest to an earlier v2 pair remains
  undetectable.
- **No timeout inside the blocking bridge read**: an unresponsive harness stalls
  the operation (fail-closed, never unverified) until the app watchdog restarts
  the host.
- **Live model-backed phone turn** on this build: **NOT RUN**.
- **200-record verification on device**: **NOT RUN** (see §10).
- The `eb51a69f…` preview store remains refused by design after the Phase 7
  tamper test; its forged bytes were archived, then the store was cleared and
  reseeded through the production route so the partition tests could run. This
  is preview fixture data, not user memory.
